# Appeals (T6.4) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A student appeals one graded question by receipt code; the teacher reviews the AI trail and decides; the student sees the outcome by receipt code; a daily Cron expires stale appeals.

**Architecture:** One new D1 table `appeals` (status column, mutable on purpose, like `grading_jobs`). Student routes in a new file mounted at `/api/exam`; teacher routes in a new file behind the existing Access middleware. A decision that adjusts the score appends a `score_revisions` row and updates the appeal in one D1 batch. No Workflows, no email.

**Tech Stack:** Hono on Workers, D1, R2 (`AUDIT`), Vitest with `@cloudflare/vitest-plugin` (app-worker); React + Vite + Vitest (app-ui).

**Spec:** `docs/superpowers/specs/2026-11-27-appeals-design.md` (extends `2026-11-25-teacher-app-cloudflare-design.md`).

## Global Constraints

- Statuses exactly: `open`, `under_review`, `upheld`, `adjusted`, `rejected`, `expired`.
- One appeal per (attempt, question); a decided or expired appeal is never refiled.
- Expiry: `open` appeals older than 14 days become `expired`.
- `score_revisions` stays append-only: never UPDATE or DELETE it; an adjustment is a new row (`source='teacher'`, reason = the note).
- Only the teacher decides. No AI opinion on appeals.
- No email, no email field, no notification hook.
- Cloudflare Free plan only; D1 Free caps queries per invocation, so each endpoint uses a fixed small number of queries (no per-row queries).
- Code comments and docs in English; student/teacher UI copy in Vietnamese like the existing pages.
- Run `app-worker` tests with `npm test` in `app-worker/`, UI tests with `npm test` in `app-ui/`.

## Review Focus

Inputs the spec implies but does not list; each has its test in the owning task.

1. Two teacher tabs decide the same appeal at once: exactly one wins, exactly one revision row (Task 1, 3).
2. A receipt from another exam, or a `problem_id` not in the exam: 404, never another student's data (Task 2).
3. Appeal on a question that is not graded yet (queued/grading): 409 (Task 2).
4. A teacher opening or deciding an appeal of someone else's exam: 404 (Task 3).
5. Blank, whitespace-only or over-long message / note; `adjusted` with a missing, non-numeric or out-of-range score: 400 (Task 2, 3).
6. R2 audit object missing: detail still answers 200 with `audit: null` (Task 3).
7. Cron boundary: an appeal exactly 14 days old is not expired, one older is; decided appeals are never touched (Task 4).

### Task 1: Table and database layer

**Files:**
- Create: `app-worker/migrations/0005_appeals.sql`, `app-worker/src/db/appeals.ts`, `app-worker/test/appeals_fixture.ts`
- Test: `app-worker/test/appeals_db.test.ts`

**Interfaces:**
- Produces (`db/appeals.ts`):
  - `type AppealStatus = "open" | "under_review" | "upheld" | "adjusted" | "rejected" | "expired"`
  - `class AppealExists extends Error`
  - `APPEAL_EXPIRY_DAYS = 14`
  - `createAppeal(db: D1Database, a: { submissionId: string; message: string; now: Date }): Promise<string>` (appeal id; throws `AppealExists`)
  - `listAppealsForAttempt(db, attemptId: string): Promise<{ problem_id: string; status: AppealStatus; message: string; decision_note: string | null; created_at: string; decided_at: string | null; score: number }[]>` (`score` = latest revision)
  - `listExamAppeals(db, examId: string): Promise<{ id: string; student_name: string; problem_id: string; status: AppealStatus; created_at: string }[]>` newest first
  - `getAppealDetail(db, appealId: string): Promise<AppealDetail | null>` where `AppealDetail` has `id, exam_id, teacher_id, student_name, problem_id, submission_id, status, message, decision_note, decided_by, created_at, decided_at, code, audit_key: string | null, revisions: { revision: number; source: string; score: number; author: string; reason: string | null; created_at: string }[]`
  - `markUnderReview(db, appealId: string): Promise<boolean>` (true only if it was `open`)
  - `decideAppeal(db, d: { id: string; decision: "upheld" | "rejected" | "adjusted"; note: string; score?: number; teacherEmail: string; now: Date }): Promise<"ok" | "already_decided">`
  - `expireStaleAppeals(db, cutoff: Date): Promise<number>` (rows expired: `open` with `created_at < cutoff`)
- Produces (`test/appeals_fixture.ts`): `seedGradedAttempt(opts?: { teacher?: string; name?: string }): Promise<{ call; examId: string; token: string; teacher: string; attemptId: string; receipt: string; problemId: string; submissionId: string }>` using `fakeGrader`, `fakeQueue`, `drain` from `test/helpers.ts` (pattern of `test/student.test.ts`): creates a one-question exam, starts an attempt, submits, drains the queue, so a revision 0 and an R2 audit object exist.

  - `createAppeal` returns an id; a second call for the same submission throws `AppealExists`.
  - `decideAppeal` with `adjusted`, score 85 → returns `"ok"`, `revisions` has a new row `{ revision: 1, source: "teacher", score: 85, reason: note, author: teacherEmail }`, appeal status `adjusted`, `decided_at` set.
  - `decideAppeal` with `upheld` → `"ok"`, no new revision row.
  - Calling `decideAppeal` twice (second as `rejected`) → second returns `"already_decided"`, revision count unchanged. Also run two calls concurrently with `Promise.all`: exactly one `"ok"`, exactly one teacher revision.
  - `markUnderReview` is true once, false the second time, and `decideAppeal` still works from `under_review`.
  - `expireStaleAppeals`: appeal created at `now - 14d` is NOT expired when cutoff = `now - 14d`; one created at `now - 14d - 1s` is; a `rejected` old appeal is untouched; returns the count.

- [ ] **Step 3:** Write `0005_appeals.sql`: `appeals(id PK, submission_id UNIQUE REFERENCES submissions(id), message, status CHECK in the six values, decision_note, decided_by, created_at, decided_at)` plus `INDEX (status, created_at)`; header comment: mutable on purpose (like `grading_jobs`). - Produces: `studentAppealRoutes(now: () => Date, verify: TurnstileVerifier): Hono<AppEnv>`

  - `RL_ACTION` that denies → 429.
